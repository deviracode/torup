# Customer appointment self-service link — design

## Problem

Customers currently confirm/cancel attendance via WhatsApp quick-reply buttons (`sendInteractiveReminder`), which only work within WhatsApp's 24h conversation-session window. For appointments booked further out, or for manually-created bookings where the customer never opened a session, these buttons silently fail to send at all (the same root cause as the missing-confirmation bug fixed in PR #18). There's also no way for a customer to request an edit or cancellation themselves — that requires calling the business directly.

## Goal

A persistent, per-appointment public link (sent via WhatsApp message templates, which bypass the 24h window) where a customer can:
1. Confirm or decline attendance (replaces the WhatsApp buttons entirely).
2. Request a date/time change, subject to the business's reschedule window and owner approval.
3. Request a cancellation, subject to the business's cancellation window and owner approval.

## Data model

### `appointments.customer_link_token` (new column)
- Random, URL-safe token (32 bytes), unique, generated by default on insert.
- Backfilled for existing rows via migration so already-scheduled appointments get a working link too.
- Public URL shape: `/{locale}/a/{token}`.

### `appointment_change_requests` (new table)
```
id                  uuid primary key
appointment_id      uuid references appointments(id)
business_id         uuid references businesses(id)
type                text check (type in ('edit', 'cancel'))
proposed_start_time timestamptz  -- edit only, null for cancel
reason              text         -- optional, cancel mainly
status              text check (status in ('pending', 'approved', 'rejected')) default 'pending'
created_at          timestamptz default now()
resolved_at         timestamptz
resolved_by         uuid references auth.users(id)
```
Constraint: at most one `pending` request per `appointment_id` (enforced at the application layer when creating a request — reject a second submission with a clear error rather than a DB-level partial unique index, to keep the migration simple).

Attendance confirm/reject needs no new table — it updates `appointments.status` + `customer_confirmed` directly, mirroring today's WhatsApp-button handler logic (`services/whatsapp-agent`).

## Public page

`apps/web/src/app/[locale]/a/[token]/page.tsx` — styled to match `booking-flow.tsx` (Tailwind utility classes, indigo accent, `rounded-xl` cards, RTL-aware via `next-intl`).

**Flow:**
1. **Phone verification gate.** Customer enters their full phone number. The page calls the backend to check it against the appointment's customer record. A mismatch returns a generic failure ("couldn't verify") with no indication of whether the token itself is valid or whose appointment it belongs to — prevents token/phone enumeration.
2. **Appointment summary + actions** (layout: all three actions visible and stacked, not hidden behind a secondary expand):
   - **✅ אני מגיע/ה / ❌** — instant. Same effect as today's WhatsApp buttons: sets `customer_confirmed` and `appointments.status` (`confirmed`/`cancelled`) immediately, notifies the business owner via WhatsApp either way.
   - **📅 בקשת שינוי מועד** — enabled only if `now < start_time - reschedule_window_minutes` (existing `booking_rules` field). Disabled state shows an explanatory note ("changes must be requested at least Xh before your appointment — please contact the business directly"). When enabled, opens the real availability picker (reuses the booking flow's date/time step + `/availability` endpoint) and submits a `pending` edit request with the chosen slot.
   - **❌ בקשת ביטול** — enabled only if `now < start_time - cancellation_window_minutes`. Optional reason field. Submits a `pending` cancel request.
   - Both request buttons disable (with "you already have a pending request") if one is already pending for this appointment.
3. After submitting a request: confirmation screen ("request sent, we'll notify you by WhatsApp"). No live status polling — outcome comes via WhatsApp notification only.
4. **Inactive appointment** (`cancelled`/`completed`/`no_show`): neutral "this appointment is no longer active" state, no actions offered.

## Backend API (public, unauthenticated — token is the auth)

- `POST /public/appointments/:token/verify` `{phone}` → on match, returns a short-lived session token (e.g. signed, ~15min TTL) scoping subsequent calls on this page load; on mismatch, generic error.
- `GET /public/appointments/:token` (requires the session token from verify) → minimal appointment info: service, date, time, business name, current pending-request state if any.
- `POST /public/appointments/:token/attendance` `{decision: "confirm"|"reject"}`.
- `POST /public/appointments/:token/change-request` `{type: "edit"|"cancel", proposedStartTime?, reason?}` — server re-validates the window gating (never trust the disabled-button state alone) and the no-existing-pending-request rule.

## Owner review (dashboard)

New "Pending Requests" section, parallel to the existing `pending_approval` bookings review UI, listing `appointment_change_requests` where `status = 'pending'` for the business. Approve/Reject actions:

- **Approve edit** → re-check slot capacity at approval time (reuse `checkSlotCapacity`); if the proposed slot is no longer available, approval fails with a message telling the owner to reject or the customer to resubmit — no silent overbooking. On success: updates `appointments.start_time`/`end_time`, marks the request `approved`, notifies the customer via WhatsApp ("your new time is confirmed").
- **Approve cancel** → re-validate the appointment's current status first (can't approve a cancel on an appointment already cancelled/completed by other means); on success sets `appointments.status = 'cancelled'`, marks the request `approved`, notifies the customer.
- **Reject either** → marks the request `rejected`, notifies the customer their request wasn't approved.

**Owner notifications** (WhatsApp, reusing the existing manager-notification pattern):
- New change request submitted (edit or cancel) — always, not gated by a setting.
- Customer confirms attendance via the link — per the original ask, the owner is notified when a customer approves their own attendance.

## WhatsApp template changes

- `appointment_reminder_he/ar` and `appointment_confirmed_he/ar` get a **URL button component** added, pointing at `https://<web-app-domain>/{locale}/a/{{1}}` with the token as the dynamic URL-suffix parameter. This is a structural template edit on Meta's side — since these 4 were already submitted/approved for at least one business (SOMAR), adding a button means resubmitting them as updated templates and waiting for a new review cycle, not a code-only change.
- `appointment_rejected_he/ar` are **not** changed — terminal state, no action needed, out of scope for this feature (matches the earlier scoping decision on template link coverage).
- `sendInteractiveReminder` (WhatsApp quick-reply Confirm/Cancel buttons) is **removed** from the reminder send path in `sendAppointmentNotification` — the `isManual` branch that currently decides between the Meta template and interactive buttons goes away; reminders always go out via the template+link now, for both manual and web/bot-originated bookings, so behavior is consistent regardless of session state.
- `sendManagerApprovalRequest` (owner approving a **new booking request** — a different, unrelated flow) is untouched.
- The inbound webhook handler for button taps (`services/whatsapp-agent`, `handleButtonResponse`) is left in place but becomes dead code once nothing sends those buttons anymore. Not cleaned up as part of this feature — flagged so it isn't a surprise later.

**Rollout ordering, to avoid a reminder gap:** deploy the template-button change and confirm Meta approval on it *before* deploying the code change that removes `sendInteractiveReminder`. If the code change ships first, reminders would fail entirely in the gap (old templates without buttons still in use, but code no longer sending interactive buttons as a fallback).

## Error handling summary

| Case | Behavior |
|---|---|
| Wrong phone number | Generic failure, no token/appointment info leaked |
| Token for inactive appointment | Neutral "no longer active" state, no actions |
| Second request while one pending | Buttons disabled, explanatory note |
| Owner approves edit, slot now taken | Approval fails, capacity re-checked server-side |
| Owner approves cancel, appointment already resolved | Approval fails, status re-validated server-side |
| Reminder sent before button-template approved | Mitigated by rollout ordering above |

## Testing

- Unit: token/phone verification (match + mismatch), change-request creation with window-gating boundary math (exactly at `cancellation_window_minutes`/`reschedule_window_minutes`), owner approve/reject transitions including the two re-validation races, and the removal of the `isManual` branch in `sendAppointmentNotification`.
- Integration: full request lifecycle — customer submits a request → owner approves → customer notified → appointment state updated correctly.

## Explicitly out of scope

- Per-business on/off toggle for the self-service feature (decided: reuse existing `booking_rules` windows only, no separate toggle).
- Link/URL button on `appointment_rejected_he/ar`.
- Cleanup of the now-dead WhatsApp button-tap webhook handler.
- Any change to `sendManagerApprovalRequest` (new-booking owner approval flow).
