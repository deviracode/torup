1 · Executive Summary

A hands-on security audit of the torup-v2 multi-tenant platform found 3 critical, 2 high, and 4 medium issues. All critical findings were exploited end-to-end against a local replica of the production stack and are believed to apply to production:

The two most urgent exposures:

  • Customer PII is publicly downloadable. The Supabase anon key — which ships inside every browser bundle — can read the entire customers table (names + phone numbers of every tenant's customers) because of an over-broad RLS policy added to fix a public-booking bug.
  • The payment webhook can be forged. POST /api/billing/webhook is unauthenticated and unverified; a fabricated payload upgrades any trial/past-due business to an active premium subscription.
  • The API rate limiter keys everyone to one bucket. No trust proxy config means every request shares a single IP-based bucket behind the load balancer — a 200-request global budget that one attacker can exhaust to take the API offline.

3 · Findings

CRIT-01 Full customer PII dump via the public anon key Critical

Summary

Migration supabase/migrations/00025_rls_gap_closure.sql adds an RLS policy that lets any unauthenticated client SELECT every row of the customers table:

CREATE POLICY "Public can read customers" ON customers FOR SELECT USING (true);

The Supabase anon key is public by design — it ships in the browser bundle (NEXT_PUBLIC_SUPABASE_ANON_KEY). Anyone can therefore download every tenant's customer records (name + phone).

Exploit (confirmed live)

curl "http://127.0.0.1:54321/rest/v1/customers?select=*" \
  -H "apikey: $ANON" -H "Authorization: Bearer $ANON"

→ [{"id":"9d7ff524…","phone":"052-9999999","name":"Secret Customer PII",…}]

Impact

Complete breach of customer privacy across all tenants — GDPR/Israeli privacy-law exposure, phishing data, reputational damage. The policy was added to fix the public-booking findOrCreate flow, but USING (true) is far broader than needed.

Remediation

  • Remove the public SELECT policy. Fix the booking flow server-side: a SECURITY DEFINER RPC (find_or_create_customer(phone, name)) that returns only the caller's row, or route customer lookup through the API with the service client.
  • If anon SELECT-by-phone is unavoidable, scope it narrowly (e.g., require phone = request.jwt.claims.phone — not feasible for anon; the RPC approach is the correct fix).
  • Add a migration 00028 revoking the policy.
CRIT-02 Billing webhook spoofing → free premium subscriptions Critical

Summary

POST /api/billing/webhook (apps/api/src/routes/billing.ts) is unauthenticated and performs no signature verification. The handler parses more_info for business_id/plan_id and activates the subscription when status_code === "000":

router.post("/webhook", async (req, res, next) => {
  try { res.json(await svc().handleWebhook(req.body)); } catch (e) { next(e); }
});

Exploit (confirmed live)

# Victim business is past_due (never paid / payment failed)
POST /api/billing/webhook  Content-Type: application/json
{"more_info":"{\"business_id\":\"<victim>\",\"plan_id\":\"<premium>\"}",
 "status_code":"000","transaction":{"uid":"FORGED"}}

→ {"received":true}
# subscriptions table: past_due → active, plan_id=premium, payplus_subscription_id="FORGED"

Impact

Complete paywall bypass. An attacker can upgrade any business (their own, or any trial/past_due business) to any paid plan for free, or downgrade competitors' payment state. Direct revenue loss.

Remediation

  • Verify the PayPlus webhook signature (check PayPlus docs for the HMAC header; PayPlus signs requests with the secret key). Reject with 401 on mismatch.
  • Alternatively/in addition: allowlist PayPlus server IPs, require idempotency keys, and validate transaction.uid matches a real pending payment before activating.
  • Never treat status_code === "000" from an unauthenticated caller as payment confirmation.
CRIT-03 Rate limiter keys all traffic to one shared bucket (global DoS) Critical

Summary

apps/api/src/app.ts uses express-rate-limit@7.5.0 but never sets app.set("trust proxy", …). Behind Railway's load balancer every request has the same req.ip, so all anonymous traffic shares one bucket (200 requests / 15 min in production).

Evidence (confirmed live)

GET /api/health  → RateLimit-Remaining: 995
GET /api/health (X-Forwarded-For: 1.2.3.4) → 994
GET /api/health (X-Forwarded-For: 5.6.7.8) → 993
…every request, from any "IP", decrements the same counter…

Impact

  • Global denial of service: 200 anonymous requests (public pages, availability, services, booking reads) exhausts the budget for the entire platform for 15 minutes. Even normal platform traffic can lock itself out.
  • No brute-force protection: per-user/per-IP limiting does nothing — login/verification attempts are never individually throttled.
  • In-memory store resets on every redeploy and is per-instance (API + worker have separate counters).

Remediation

  • Set app.set("trust proxy", 1) (or the correct hop count) so req.ip resolves to the real client IP from X-Forwarded-For.
  • Back the limiter with Redis (REDIS_URL already exists) so limits are shared across instances and survive deploys.
  • Separate, stricter limits for auth endpoints (login, resend-confirmation, OTP) keyed by IP.
HIGH-01 Mass assignment on shared customer records → cross-tenant data corruption High

Summary

PATCH /api/businesses/:businessId/customers/:customerId (apps/api/src/routes/customers.ts) requires only membership (no role check) and passes the raw request body straight into .update(data) on the customers table. Customers are shared across businesses (identified by phone) — so any member of any business that has an appointment with a customer can rewrite that shared record.

Exploit (confirmed live)

# User B (member of business B only) rewrites a shared customer
PATCH /api/businesses/<bizB>/customers/<customer>   {"phone":"050-0000000","name":"CORRUPTED"}

→ 200 {"id":…,"phone":"050-0000000","name":"CORRUPTED",…}
# Row changed for ALL businesses that share this customer

Arbitrary columns are accepted (e.g., language_preference) — no field whitelist.

Impact

Cross-tenant data corruption; a malicious member can hijack a customer's identity by changing their phone (breaking other businesses' appointment links), or poison shared contact data.

Remediation

  • Whitelist updatable fields per endpoint (name/phone only where intended) — never pass req.body wholesale.
  • Review the RLS UPDATE policy (00025): it has USING but no WITH CHECK, so arbitrary column values are allowed.
  • Apply the same whitelist audit to PATCH /businesses/:id, configuration, services, categories, and staff update paths (same raw-body pattern).
HIGH-02 Anonymous booking abuse — direct DB inserts bypass booking rules High

Summary

The public anon key can insert directly into appointments (RLS: "Anyone can create appointments" with only a business-active WITH CHECK) — with any column values, including status: "confirmed", arbitrary times, and no availability, capacity, or approval-flow enforcement. Anon can also create unlimited customers rows.

Exploit (confirmed live)

# Anonymous insert of a CONFIRMED appointment at 3 AM
POST /rest/v1/appointments  (apikey: $ANON)
{"business_id":"<victim>","customer_id":…,"service_id":…,
 "start_time":"2026-08-07T03:00:00Z","end_time":…,"status":"confirmed"}

→ HTTP 201 · row inserted with status = confirmed

# Anonymous customer spam (pre-register phone numbers)
POST /rest/v1/customers → 201 (repeatable, unlimited)

Impact

  • Calendar poisoning / booking DoS: an attacker floods a tenant's calendar with fake confirmed appointments, or books all time slots.
  • Phone pre-registration: registering a victim's number before they book triggers the UNIQUE(phone) constraint and breaks their booking.
  • Bypass of the owner-approval workflow and any paid/limit-based booking rules.

Remediation

  • Move booking creation server-side (API route with service client) and enforce availability/capacity/status transitions in code.
  • Constrain the RLS INSERT policy: default status to pending via column default or trigger; WITH CHECK (status = 'pending').
  • Consider limiting anonymous customer creation (e.g., require a valid format + per-IP throttle at the edge).
MED-01 Internal worker endpoints guarded by a single shared master secret Medium

Summary

All /api/internal/* routes (reminders tick, notify-manager, appointment approve/reject, Google Calendar sync) are protected by one shared INTERNAL_SECRET compared with a timing-unsafe !== and with no rate limit. There is no per-business scoping.

Exploit (confirmed live)

POST /api/internal/appointments/<anyTenantAppointment>/approve
  Header: x-internal-secret: test-internal-secret
→ {"approved":"cc6c202f…"}   (appointment in a *different* tenant: pending_approval → confirmed)

Impact

Whoever holds the secret (env leak, logs, misconfig) can approve/reject appointments and trigger notifications for every tenant. Timing-unsafe comparison weakens the secret against timing attacks; no rate limit invites brute force.

Remediation

  • Compare with crypto.timingSafeEqual.
  • Scope approve/reject to the business owning the appointment (lookup + membership of the calling service), or per-tenant secrets.
  • Add a rate limit and restrict /api/internal to the private network domain only (Railway private networking).
MED-02 Production secrets committed to git Medium

Summary

apps/api/.env.example (committed) contains the real production Supabase project URL, the anon key, and — critically — the service_role key (full database admin, bypasses RLS). Anyone with repo access has complete database control.

SUPABASE_URL=https://xewiqmxzhxlhmgspairk.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi…        # public by design
SUPABASE_SERVICE_ROLE_KEY=eyJhbGciOi… # FULL DB ADMIN — must not be committed

Remediation

  • Replace all values in committed .env.example files with placeholders.
  • Rotate the service_role key and anon key (assume exposure).
  • Scan git history and purge leaked keys; consider git filter-repo or key rotation as the primary mitigation.
MED-03 Rate limiter is in-memory and per-instance (doesn't survive deploys) Medium

Beyond the keying bug (CRIT-03), the limiter store is in-memory: it resets on every deploy, and API + worker instances each maintain independent counters. Combined with the shared bucket, the limiter provides neither protection nor stability. The resendCooldowns map in routes/auth.ts is likewise in-memory and unbounded (slow memory-growth DoS).

Remediation: Redis-backed store (already have REDIS_URL); replace the cooldown map with Redis TTL keys.

MED-04 Auth-callback redirect value is unvalidated Medium

apps/web/src/app/auth/callback/route.ts concatenates a user-supplied next query parameter into the post-login redirect URL (${origin}${next}). String concatenation prevents the trivial absolute-URL redirect, but the value is never validated against an allowlist (protocol-relative and backslash tricks can be fragile across clients).

Remediation: Validate next against an allowlist of in-app paths (^/[\w-/]+$, must not start with // or contain :), else fall back to /he/dashboard.

LOW-01 Email enumeration risk on resend-confirmation (verify in prod) Low

POST /api/auth/resend-confirmation forwards Supabase's error message verbatim (throw new AppError(400, error.message)). Locally, Supabase returned success for both existing and non-existing addresses, so enumeration was not demonstrable — but if the production Supabase error for unknown users differs from the success path, account existence can be probed. The 60-second cooldown is also trivially bypassed by rotating email addresses.

Remediation: Return a generic message on all outcomes; log the Supabase error server-side only.

4 · What Verified OK ✅

  • Tenant isolation middleware — cross-tenant matrix returned 403 for appointments, customers, staff, waitlist, analytics, business PATCH, and WhatsApp credentials when user A (owner of biz A) accessed biz B. Both owners could access their own businesses (200).
  • WhatsApp webhook security — GET verify endpoint: 403 on wrong per-tenant token, 200 on correct; POST: 403 on invalid HMAC signature (timingSafeEqual), plus inbound payload phone-number match against the credential.
  • RLS enabled on all 18 tables (businesses → whatsapp_credentials, incl. Google Calendar tokens with no anon/authenticated policies).
  • No XSS vectors in the web app (no dangerouslySetInnerHTML/innerHTML/eval).
  • No tokens in URLs — API uses Authorization: Bearer; no localStorage session storage; PKCE flow for password reset; cookie flags from @supabase/ssr defaults (HttpOnly, SameSite=Lax, Secure in prod).
  • helmet() defaults (CSP, HSTS via upgrade-insecure-requests, COOP/CORP) active — verified in response headers.
  • Admin routes — all behind requireRole("super_admin").
  • Internal routes require the secret — 401 without x-internal-secret.
  • Public business/services reads are intentionally anon and scoped by RLS to active businesses only.

5 · Infrastructure Recommendations (Railway IaC)

Beyond the code fixes, the deployment layer should be hardened. Railway itself does not offer a managed WAF, so the options are:

OptionWhat it addsEffort
A. Cloudflare in front (recommended)Edge rate limiting, WAF rules, bot mitigation, DDoS protection, TLS. Point the custom domains at Cloudflare and set Railway to "Cloudflare proxy" trusted proxies (app.set("trust proxy", …) for Cloudflare's headers).Medium
B. Redis-backed rate limitingShared, persistent limits across API + worker instances; per-IP + per-token keys; survives deploys. Requires trust proxy fix first (CRIT-03).Low
C. Railway private networkingRestrict /api/internal and database/Redis traffic to the private network; do not expose internal endpoints publicly.Low
D. App-level limitsStricter per-IP limits on auth endpoints; input validation whitelists; HMAC verification for billing webhook.Low-Medium

Recommended order: fix CRIT-02 (webhook HMAC) and CRIT-01 (RLS) in code first; then CRIT-03 (trust proxy + Redis limiter); then B+C; then evaluate A as a hardening layer.
